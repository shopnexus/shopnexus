# server2 Plan 1: platform Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.
>
> This plan is executed by the user, who types all product code. Claude reviews each task before the next one starts and does not write product code. Steps therefore give exact interfaces, test cases with inputs and expected results, hints and traps, and no ready-made implementation.

**Goal:** A running Go server in `~/shopnexus/server2` with config, telemetry, Postgres access and migrations, the OpenAPI-first HTTP layer, the `account` module, and the outbox → relay → JetStream job pipeline, all tested.

**Architecture:** One binary built by `internal/app`, wired by hand. Platform packages under `internal/platform` know no business module. Modules are single packages with one file per use case. Every outside effect leaves through the Postgres outbox, a single relay, and JetStream consumers.

**Tech Stack:** Go 1.27.2 (standard library `net/http`, `log/slog`, `encoding/json`, `embed`, `uuid`), PostgreSQL 19 RC 1, pgx v5, NATS 2.15.1 with JetStream, kin-openapi, OpenTelemetry Go SDK, grafana/otel-lgtm, Prism.

**Spec:** `~/shopnexus/specs/2026-10-19-server2-foundation-design.md`. Plan 2 (auth flows, tokens, Google, the `/v1/accounts/me` endpoints, the observability exercise) is written after this plan is done, so it can build on the code as it turned out.

## Global Constraints

- Module path `github.com/shopnexus/server2`; repository `~/shopnexus/server2`, its own git repository.
- Newest release of every component; library versions are whatever `go get <module>@latest` returns on the day, pinned in `go.mod`.
- SQL by hand in Go; no sqlc, ORM, query builder or code generation.
- Allowed third-party modules in product code: pgx v5, kin-openapi, golang-jwt v5, go-oidc v3, golang.org/x/crypto, nats.go, OpenTelemetry. Test code may also use `github.com/nats-io/nats-server/v2`.
- IDs are the standard library `uuid.UUID` (Go 1.27), generated by Postgres `uuidv7()`.
- `platform` never imports a module; `auth` imports `account`, never the reverse.
- A transaction is passed as `postgres.Querier`, never through `context`.
- No raw database error, constraint name or stack trace reaches an HTTP client.
- Passwords, OTP codes, tokens and refresh tokens never appear in logs.
- Tests compile on every run (no build tags). Integration tests skip under `-short` and fail when their service is missing.
- Dev ports: Postgres 56432, NATS 56222 (monitoring 56822), Grafana 56300, OTLP gRPC 56317 and HTTP 56318, Prism 56400, server 8080. Test stack: Postgres 56433.

## Review Focus

1. An operator starts the server with migrations pending: it must refuse to start and name `make migrate`, not serve requests against an old schema. Pinned in Task 3, step 3 (`internal/app/app_test.go`).
2. A request body that is not JSON, empty, or over 1 MB on any route: a 400 or 413 in the shared error format, never a 500 or a Go error string. Pinned in Task 4, step 3.
3. `go test ./...` run by mistake against the development database: `testdb` must refuse before touching it. Pinned in Task 3, step 3.
4. The relay dies after JetStream accepted a message and before `published_at` was written: exactly one message in the stream after restart. Pinned in Task 6, step 5.
5. Two server instances running at once: one relay publishes, the other waits; migrations never run twice. Pinned in Task 3, step 5 and Task 6, step 5.

## How each task runs

1. Read the task, then the spec sections it names.
2. Write the tests from the test-case tables. Run them and watch them fail for the stated reason.
3. Implement until they pass. Use the hints; read the traps before starting.
4. Run `make lint` and the task's test command.
5. Answer the check question in chat, then ask Claude for review. Fix review findings.
6. Commit with a message saying what the task added.

- [ ] **Step 2: `testenv` and `testdb`**

`testdb.New`:
1. Parse `testenv.DatabaseURL(t)`. Refuse (`t.Fatal`) unless the port is `56433` and the database is `server2_test`.
2. Compute a hash over every migration checksum. The template database is `server2_tpl_<first 12 hex>`. When it does not exist, create it under `pg_advisory_lock` and run `Migrate` into it. A new migration therefore produces a new template.
3. Clone with `CREATE DATABASE t_<random> TEMPLATE server2_tpl_<hash>`, serialised by the same advisory lock, and return a pool for it.
4. `t.Cleanup`: close the pool, `DROP DATABASE ... WITH (FORCE)`.

Traps: `go test ./...` runs package test binaries in parallel processes, so a `sync.Once` alone does not stop two processes building the template; the advisory lock does. `CREATE DATABASE ... TEMPLATE` fails while any session is connected to the template; close the pool you migrated with before cloning. Database names cannot be bind parameters; build them from hex only, never from input.

- [ ] **Step 5: Implement**

Hints:
- `Migrate` acquires one connection from the pool (`pool.Acquire`) and runs `pg_advisory_lock` on it. Session-level advisory locks belong to a connection; locking through the pool can lock on one connection and unlock on another.
- Each migration runs in a transaction on that connection together with its `schema_migrations` insert.
- Checksum: `sha256.Sum256([]byte(sql))`, stored as `bytea`.
- `InTx`: `pool.Begin`, `defer tx.Rollback(ctx)` (a no-op after commit), call `fn(tx)`, then `tx.Commit`.
- The tracer implements `pgx.QueryTracer` (`TraceQueryStart` returns a context carrying the span; `TraceQueryEnd` ends it, records `RowsAffected` from the command tag and the error). Set it in `pgxpool.Config.ConnConfig.Tracer`.
- Pool metrics: observable gauges reading `pool.Stat()` (`AcquiredConns`, `IdleConns`, `TotalConns`, `AcquireDuration`).
- If pgx does not scan `uuid` into the standard library `uuid.UUID` directly, register a type or scan into `[16]byte` and convert; the `querier_test` case decides.
