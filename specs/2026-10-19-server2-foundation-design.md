# Design: server2 foundation (stack, platform, observability, auth)

Date: 2026-10-19
Status: decided in conversation on 2026-10-19, section by section. The user
approved each section after the questions recorded under "Decision record".

## Goal

`~/shopnexus/server2` is a new Go backend that will replace `server`. This
first phase builds everything that has no business rules in it: the project
skeleton, the platform packages, observability, the job pipeline, and
authentication with phone OTP, email OTP, username-style password login and
Google sign-in. Listings, deals, orders and the other business modules come in
later phases on top of this one.

`server` is not reused. It has a five-package hexagonal layout per module, fx
wiring, eight database pools pointing at one database, two event buses, and
119 of its 161 handlers answer 501. server2 keeps the parts that held up
(modular monolith by business area, provider seams for vendors, rich entity
methods in `account`) and drops the rest.

## Working mode

The user types all product code. Claude writes this spec and the plan,
explains, answers questions and reviews each step. The plan therefore gives
each step a goal, acceptance criteria, hints and known traps, and no
ready-made code. Claude asks a check question at decisions that touch

## Scope

In this phase:

- repository, Go toolchain, Docker Compose stacks, Makefile
- platform packages: config, telemetry, postgres, httpx, authn, jobs, testdb, testenv
- providers: SMS and email senders that write to the log
- module `account`: profile, status, suspension
- module `auth`: identities, passwords, OTP challenges, sessions, Google
- OpenAPI spec for every endpoint above, with conformance tests
- an observability exercise (an N+1 query and a missing index found through traces)

Later phases:

- business modules (listing, deal, order, chat, kyc, notification)
- a real SMS and email vendor
- the event layer on top of jobs (`events.Publish`, ordering keys)

- Play Integrity checks on OTP requests
- CI, production deployment, the `server2` submodule in the umbrella repository

SQL is written by hand in Go files. There is no sqlc, ORM, query builder or
code generation. `go-playground/validator` is not used, because request shape
is validated against the OpenAPI spec (see "Request validation").

The user wants the newest release of every component. Versions on
2026-10-19: Go 1.27.2, PostgreSQL 19 RC 1 (general availability planned for
2026-11-19; 18.6 is the current stable release), NATS 2.15.1, OpenAPI 3.2.
Library versions are the newest at the time `go.mod` is created, pinned in
`go.mod`. Development and test stacks run `postgres:19rc1` and move to
`postgres:19` on its release; both stacks hold only disposable data, so a
catalog change between the candidate and the release costs a drop and a
re-migration. Production runs a released major version only.

kin-openapi reads OpenAPI 3.2 in part (3.0 and 3.1 fully, plus the 3.2 QUERY
method, `additionalOperations` and `itemSchema`). Step 4 checks that
kin-openapi validates and Prism serves a 3.2 document. If either fails, the
spec is written as 3.1 using no 3.2 features, and moves to 3.2 when the tools
accept it.

## Code organisation

A module is one Go package. A file holds one use case: a struct whose fields
are the dependencies that use case needs, its input and output types, an
`Execute` method, and a `Handler` method at the bottom when the use case has a
route. File names put the noun first (`account_create.go`,
`account_status.go`) so files about one entity sort together.

```go
type AccountRename struct {
    Store Store
    Tx    postgres.TxRunner
    Now   func() time.Time
}

func (uc AccountRename) Execute(ctx context.Context, id uuid.UUID, in AccountRenameInput) (AccountView, error)
func (uc AccountRename) Handler(log *slog.Logger) http.Handler
```

`routes.go` holds the module's `Deps` struct and `Routes(r, d)`, which builds
every HTTP use case from `Deps`. Only `Routes` and `app.go` read `Deps`. A test
fills only the fields of the use case under test, so a dependency added to one
use case changes only that use case's tests.

Each module has entity files (`account.go`), small store interfaces per
aggregate (`account_store.go`), a Postgres adapter (`account_store_pg.go`) and,
in `<module>test/`, an in-memory fake plus a contract test suite that runs
against both the fake and the Postgres adapter.

A rule goes into an entity method when it needs only the entity's fields and
its arguments (including `now`). Reading or writing the database, calling
vendors and touching other aggregates belong to the use case. When an entity
needs an outside fact, the use case fetches it and passes it in. A rule that
spans rows or accounts is enforced by a database constraint; Go code checks
it early for a better error, and the constraint is what holds.

Entities keep fields unexported when an invariant protects them. The store
lives in the same package and can still read and write them.

### Feature subpackages

A module moves its features into subpackages when it passes about 30 files,
not counting tests. `auth` starts with them: its endpoints alone come to 16
use cases.

A subpackage holds one aggregate: the entity, its store, the Postgres adapter,
the rules that need only that aggregate, and a `<feature>test/` package with
the fake and the contract suite. It has no HTTP handlers and does not open
transactions; its methods take a `postgres.Querier`. It imports `platform` and
nothing else from its module, so no subpackage imports a sibling.

The parent package holds every use case. A use case opens the transaction,
calls the subpackages in order and ends with its HTTP handler, so the sign-in
flow (check the code, find or create the identity, create the account, issue a
session) is read top to bottom in `auth/otp_verify.go`.

```
auth/
  otp_send.go  otp_verify.go  password_login.go  ...  routes.go  middleware.go
  otp/         OTP challenges
  identity/    identities and the count behind the last-identity rule
  password/    argon2id hashing, the passwords table
  session/     sessions, refresh rotation, JWT signing and parsing
  google/      ID token verification, nonces
  throttle/    auth_throttle counters
```

`platform/contact` normalises phone numbers and email addresses.
`contact.ParsePhone` and `contact.ParseEmail` return types that hold only
normalised values, and `otp` and `identity` accept only those types.
`UNIQUE (kind, value)` on identities depends on both packages normalising the
same way.

## Module boundaries

`account` owns who a person is: display name, status, suspension. It knows
nothing about login.

`auth` owns how a person proves it: identities, the password, OTP challenges,
sessions, Google sign-in, and the rule that an account keeps at least one
identity.

`auth` imports `account`; `account` never imports `auth`. Go rejects import
cycles at compile time. `auth` declares one small interface for each
`account` use case it calls, and `app.go` passes the use case in:

```go
// auth/accounts.go
type accountCreator interface {
    Execute(ctx context.Context, q postgres.Querier, displayName string) (uuid.UUID, error)
}

type accountStatus interface {
    Execute(ctx context.Context, q postgres.Querier, id uuid.UUID) (account.Status, error)
}
```

`account.AccountCreate` and `account.AccountStatus` satisfy these without
naming them. Tests in `auth` pass fakes and never build an `account` store.

Suspending an account changes `accounts.status` and calls nothing in `auth`.
`auth` reads the status at login and at refresh.

Other modules learn who is calling from `platform/authn`, which `auth`'s
middleware fills. Business modules do not import `auth`.

`platform` never imports a module.

## Transactions

```go
// platform/postgres
type Querier interface {
    Exec(ctx context.Context, sql string, args ...any) (pgconn.CommandTag, error)
    Query(ctx context.Context, sql string, args ...any) (pgx.Rows, error)
    QueryRow(ctx context.Context, sql string, args ...any) pgx.Row
}

type TxRunner interface {
    InTx(ctx context.Context, fn func(q Querier) error) error
}
```

Store methods take a `Querier`. Use cases take a `TxRunner`. A transaction is
passed as an argument, never through `context`. A use case test passes a fake
`TxRunner` that calls `fn(nil)`, and fake stores ignore the `Querier`.
Rollback behaviour is tested in the Postgres adapter tests.

A use case that reads a row, changes it and writes it back reads with the
store's `GetForUpdate`, which adds `FOR UPDATE`. With a plain `Get`, a write
committed between the read and the `Update` is lost: a rename that read the
account before an admin suspended it would write `status = active` back.

A transaction that spans modules (first sign-in creates an `accounts` row and
an `identities` row) is opened by `auth` and the same `Querier` is passed to
`account.Create`.

Transactions stay short. Vendor calls never run inside one.

No table in this phase has a `version` column. OTP verification locks the
challenge row with `SELECT ... FOR UPDATE`. Session rotation uses the old
refresh hash as its condition. Optimistic locking with `version` is for later
entities that several people edit.

## API contract

The API is OpenAPI first. `api/openapi.yaml` is written before the code, and
the code has to satisfy it. Four tests hold the code to the spec:

1. The spec loads and validates with kin-openapi, `$ref`s included.
2. Routes registered through `httpx` equal the operations in the spec, in both
   directions. An operation without a route fails, and so does a route
   without an operation.
3. The E2E HTTP client validates every response (status, headers, body)
   against the operation it called.
4. Every status code an operation declares is observed in at least one E2E
   test. The suite fails at the end when a declared status was never seen.

The `mock` Compose profile runs Prism on the spec, so app2 can call a fake
server2 before the real one exists.

Each endpoint is built in this order: spec, review, failing E2E test, entity
and use case and store with their tests, passing E2E test.

## HTTP layer

`http.ServeMux` with method and path patterns (`GET /v1/accounts/{id}`). Every
API route starts with `/v1`; a breaking change to a route adds `/v2` beside it,
because app installs stay on old versions for months.

Middleware is `func(http.Handler) http.Handler`. Order from the outside in:
recover, request ID, trace span, access log, route, then the sign-in
requirement on routes that need it.

### Request validation

A kin-openapi middleware validates each request against its operation before
the handler runs. Validation errors map to the shared error format with one
entry per field in `fields`. Shape rules (required, length, format, enum) live
only in the spec. Business rules live in entities.

The body is capped at 1 MB with `http.MaxBytesReader`. Unknown fields are
rejected (`additionalProperties: false` in the spec). JSON uses `snake_case`.

### Errors

```json
{
  "error": {
    "code": "invalid_code",
    "message": "the code does not match",
    "fields": { "code": "mismatch" },
    "trace_id": "4bf92f3577b34da6"
  }
}
```

`code` is stable and machine-readable; app2 maps it to Vietnamese text.
`message` is English for developers. Entities and use cases return errors with
a kind (`NotFound`, `Conflict`, `Invalid`, `Unauthenticated`, `Forbidden`,
`RateLimited`, `PreconditionRequired`) and a code; only `httpx` maps a kind to
an HTTP status. An unexpected error returns 500 with a generic message, and
the real error goes to the log with the same `trace_id`. Raw database errors
never reach a client, because they reveal table and constraint names and
whether a value exists.

A resource the caller may not see returns 404, never 403. Every read or write
by ID checks ownership, normally in the query itself
(`WHERE id = $1 AND owner_id = $2`). An E2E test per resource checks that
account B gets 404 for account A's resource.

### Pagination and server lifecycle

Lists use a cursor: `?cursor=...&limit=20` returns `{items, next_cursor}`.
UUIDv7 sorts by creation time, so `id` is the cursor.

The server sets read-header 5 s, read 15 s, write 30 s and idle 60 s
timeouts. On SIGTERM it stops accepting requests and waits up to 15 s for the
ones in flight.

## Configuration

Configuration comes from environment variables, read once at start into a
struct in `platform/config`. Missing or invalid variables stop the process,
and the message lists all of them at once. In development a `.env` file (git
ignored) is read by a short loader that sets only variables the environment
does not already have. `.env.example` is committed and lists every variable.
Business code never calls `os.Getenv`; each module receives its part of the
config through its constructor.

## Database and migrations

PostgreSQL 19. Primary keys are `uuid DEFAULT uuidv7()` (available since 18). UUIDs are unique across
databases, which keeps data merges and imports free of key collisions, and
they do not reveal how many rows exist. They do not replace ownership checks.

Migrations are plain SQL files in `migrations/`, embedded with `embed`, run by
a runner of about 80 lines in `platform/postgres`:

1. Create `schema_migrations(version, name, checksum, applied_at)` if missing.
2. Take a Postgres advisory lock so two processes never migrate at once.
3. Apply each pending file in its own transaction and record its SHA-256.
4. Compare the checksum of each applied file and stop with an error when one
   changed.

Migrations only go up. A mistake is fixed by a new migration. The server does
not migrate; `make migrate` does. At start the server refuses to run when
migrations are pending.

## Jobs and the broker

Every effect outside the database (SMS, email, later push, webhooks, events)
goes through a transactional outbox, so a crash between commit and send loses
nothing.

```
use case ─(same tx)─► outbox table ──► relay ──► JetStream ──► consumer ──► vendor
```

### Outbox

```
outbox
  id            uuid DEFAULT uuidv7()
  subject       text         -- "cmd.sms.send"
  payload       jsonb
  deadline      timestamptz NULL
  ordering_key  text NULL    -- unused in this phase
  created_at    timestamptz
  published_at  timestamptz NULL
```

A partial index on `id WHERE published_at IS NULL` keeps the pending scan
small. Published rows older than 7 days are deleted in batches.

### API for modules

```go
type SendSMS struct {
    To   string `json:"to"`
    Text string `json:"text"`
}
func (SendSMS) Subject() string { return "cmd.sms.send" }

jobs.Enqueue(ctx, q, SendSMS{To: to, Text: text}, jobs.Deadline(c.ExpiresAt))

jobs.Handle(ctx, consumers, jobs.Options{Concurrency: 8}, func(ctx context.Context, m SendSMS) error {
    return sms.Send(ctx, m.To, m.Text)
})
```

`Enqueue` writes an outbox row with the caller's `Querier`, so it commits or
rolls back with the business data. `Handle` creates a durable consumer for the
payload type's subject and decodes each message into that type. Use cases and
handlers never see NATS.

### Relay

One relay runs at a time. It holds a Postgres advisory lock on a dedicated
connection; other instances wait for the lock. It reads pending rows in `id`
order and publishes them one at a time, waiting for JetStream's
acknowledgement before it sets `published_at`. On a publish error it retries
the same row, so messages enter the stream in outbox order. Each message
carries `Nats-Msg-Id = outbox.id` and, when set, a `Deadline` header. A
Postgres `NOTIFY` after commit wakes the relay; it also polls every 2 s.

### Streams

| Stream | Subjects | Retention | Use |
|---|---|---|---|
| `CMD` | `cmd.>` | WorkQueue | commands: SMS, email |
| `EVT` | `evt.>` | Limits, 7 days | business events (later phases) |
| `DLQ` | `dlq.>` | Limits, 30 days | messages that ran out of attempts |

`CMD` and `EVT` deduplicate on `Nats-Msg-Id` over a 10-minute window.

### Consumers

Each handler is a durable pull consumer with `MaxAckPending` equal to its
concurrency, `BackOff` of 1 s, 4 s, 16 s, 64 s and `MaxDeliver` 5. A message
whose `Deadline` has passed is acknowledged without running the handler. When
JetStream publishes the max-deliveries advisory, a platform goroutine copies
the message to `dlq.<original subject>` and logs an error, which raises the
DLQ metric.

Delivery is at least once. The broker deduplicates only relay retries inside
its window; a consumer that sends and then dies before acknowledging gets the
message again. Handlers therefore tolerate duplicates. A duplicate SMS is
accepted. Handlers that move money in later phases record the message ID in
the same transaction as their change and skip IDs they have seen.

### Event layer

The event layer is built in a later phase. `events.Publish(ctx, q, OrderPlaced{...})` will write one outbox row on
`evt.order.placed`. Each listener is a consumer on that subject. Events of one
aggregate that must arrive in order will use JetStream subject mapping to
spread subjects over N partitions by key, with one consumer per partition and
`MaxAckPending` 1. A message that fails for good blocks its partition and
raises an alert; it is not skipped. A listener that does not need order reads
the aggregate's current state instead.

## Observability

Development runs one `grafana/otel-lgtm` container (collector, Grafana,
Tempo, Loki, Prometheus) under the `obs` Compose profile.

Logs: `slog` writes text in development and JSON in production
(`LOG_FORMAT`). A wrapping handler adds `trace_id` and `span_id` from the
context. Logs are also exported over OTLP through `otelslog`. Passwords, OTP
codes, tokens and refresh tokens are never logged; phone numbers are masked
(`+8490****567`). The development SMS and email senders are the one exception:
writing the message to the log is their job.

Traces: the OTel SDK exports over OTLP/HTTP to port 4318. A hand-written HTTP
middleware reads `traceparent` and opens a span named by the route pattern. A
hand-written pgx `QueryTracer` opens a span per query with the SQL text and
rows affected. Development samples every request.

Metrics, labelled by route pattern and never by raw path:

- HTTP request count and duration histogram by `route`, `method`, `status`
- pgx pool: acquired, idle, total, acquire wait time
- outbox: pending rows, age of the oldest pending row, publish lag
- JetStream: unacknowledged messages per consumer, DLQ count
- auth: `otp_sent_total`, `login_total{method,result}`, `refresh_reuse_total`, `dormant_phone_login_total`

## Auth data model

```
accounts (module account)
  id                uuid PK DEFAULT uuidv7()
  display_name      text NULL         -- empty until the profile is completed
  status            text NOT NULL     -- active | suspended
  suspended_until   timestamptz NULL
  suspend_reason    text NULL
  created_at, updated_at

identities (module auth)
  id                uuid PK
  account_id        uuid NOT NULL REFERENCES accounts
  kind              text NOT NULL     -- phone | email | google
  value             text NOT NULL     -- E.164 phone, lower-case email, Google sub
  last_used_at      timestamptz NULL
  created_at
  UNIQUE (kind, value)

passwords (module auth)
  account_id        uuid PK REFERENCES accounts
  hash              text NOT NULL     -- PHC string, argon2id
  updated_at

sessions (module auth)
  id                uuid PK           -- the sid claim
  account_id        uuid NOT NULL REFERENCES accounts
  refresh_hash      bytea NOT NULL UNIQUE
  prev_refresh_hash bytea NULL
  device_name       text NULL
  created_at, last_used_at, expires_at
  revoked_at        timestamptz NULL

otp_challenges (module auth)
  id                uuid PK
  purpose           text NOT NULL     -- login | add_identity | reset_password
  kind              text NOT NULL     -- phone | email
  destination       text NOT NULL     -- normalised
  account_id        uuid NULL         -- set for add_identity
  code_hash         bytea NOT NULL    -- HMAC-SHA256(OTP_KEY, code)
  attempts          int NOT NULL DEFAULT 0
  ip                inet NOT NULL
  expires_at, created_at
  consumed_at       timestamptz NULL
  INDEX (destination, created_at), INDEX (ip, created_at)

auth_throttle (module auth)
  key               text PK           -- "pw:+84901234567", "pw-ip:1.2.3.4"
  window_start      timestamptz NOT NULL
  count             int NOT NULL
```

Every identity row is verified; a value waiting for verification is an OTP
challenge. Values are normalised before every insert and lookup, or `UNIQUE`
would treat `0901234567` and `+84901234567` as two numbers. Foreign keys go
from `auth` tables to `accounts` and never the other way.

### Hashing

The hash follows how guessable the value is:

| Value | Possibilities | Stored as |
|---|---|---|
| refresh token, 32 random bytes | 2^256 | SHA-256 |
| OTP, 6 digits | 10^6 | HMAC-SHA256 with `OTP_KEY` from config |
| password, chosen by a person | small in practice | argon2id |

A leaked database with SHA-256 OTP hashes gives up every pending code in under
a second; the HMAC key is not in the database. The plan includes a test that
measures that second.

## Tokens

### Access token

JWT signed with EdDSA (Ed25519). Only `auth` holds the private key; any
service can verify with the public key. Verification accepts only EdDSA
(`WithValidMethods`), which closes `alg: none` and algorithm-swap attacks.
The header carries `kid`; config holds the current key and the previous one so
a key change does not sign anyone out.

Claims: `iss`, `aud`, `sub` (account ID), `sid` (session ID), `auth_time`
(when the person last proved who they are; refresh keeps it), `iat`, `exp`
(15 minutes). Clock skew allowance is 30 s. No phone, email or name goes into
the token, because anyone holding it can read it.

The middleware checks signature and expiry and puts
`Principal{AccountID, SessionID, AuthTime}` in the context. It does not query
the database. There is no revocation list. A suspended person keeps read
access until the access token expires; write use cases load the account and
call `a.CanWrite(now)`, so writes stop at once.

### Refresh token

32 random bytes, base64url, prefix `rt_`, stored as SHA-256. Sessions expire
60 days after creation or 30 days after last use.

`POST /v1/auth/refresh`:

1. Hash the token and find the session by `refresh_hash`. When no session has
   it but one has it as `prev_refresh_hash`, the old token was replayed:
   revoke that session, return `session_revoked`, log a security event and
   raise `refresh_reuse_total`. When nothing matches, return
   `invalid_refresh_token`.
2. Reject revoked and expired sessions.
3. Read the account status. A suspended account gets its session revoked and
   `account_suspended`.
4. Rotate with
   `UPDATE sessions SET refresh_hash = $new, prev_refresh_hash = $old, last_used_at = now() WHERE id = $id AND refresh_hash = $old`.
   Zero rows means a concurrent refresh won; treat it as a replay.
5. Return a new access token and refresh token.

### Logout and devices

`POST /v1/auth/logout` revokes the session in `sid`. The access token stays
valid for at most 15 minutes and the app discards it. `POST /v1/auth/logout-all`
revokes every session. `GET /v1/auth/sessions` lists devices (name sent at
sign-in, last use), and `DELETE /v1/auth/sessions/{id}` signs one out.

### Recent sign-in

Removing an identity, setting the first password and `logout-all` require
`auth_time` within the last 15 minutes. Otherwise they return
`reauth_required` and the app asks for an OTP or the password again.

## Auth flows

No flow reveals whether an account exists to someone who has not proved
ownership of the phone, email or Google account in question.

### OTP sign-in and sign-up

`POST /v1/auth/otp` with `{kind, destination, purpose: "login"}`:

1. Normalise the destination. Phones must be `+84` in this phase.
2. Check limits by counting `otp_challenges`: one code per destination per
   45 s, five per destination per hour, twenty per IP per hour.
3. Generate six digits with `crypto/rand`, store the HMAC, expire in 5 minutes.
4. Enqueue `SendSMS` or `SendEmail` with `Deadline = expires_at`, in the same
   transaction.
5. Return `{challenge_id, resend_after: 45}` whether or not an account exists.

`POST /v1/auth/otp/verify` with `{challenge_id, code, device_name}`, in one
transaction:

1. Load the challenge `FOR UPDATE`. It must be the newest challenge for its
   destination and purpose.
2. Call `c.Verify(code, now)`. A wrong code saves `attempts` and returns
   `invalid_code` with `attempts_left`; expiry returns `code_expired`; five
   wrong codes return `code_locked`.
3. On a match set `consumed_at` and look up the identity.
   - It exists: check the account status (`account_suspended` is safe to
     return now) and apply the dormant check below.
   - It does not exist: create the account through `account.Create` with the
     same `Querier`, then the identity.
4. Create a session and return tokens and `{account: {id, is_new}}`.
   `is_new` sends app2 to "Hoàn thiện hồ sơ".

### Dormant phone accounts

Carriers reassign numbers that sit unused. An OTP sign-in by phone to an
account whose phone identity was last used more than 6 months ago:

- When the account has another identity or a password, the verify step
  returns `step_up_required` with the other methods masked. The person signs
  in with one of them to finish.
- When the phone is the only method, sign-in proceeds as usual in this phase,
  and the server logs a security event and raises
  `dormant_phone_login_total`. This is a known, accepted risk until the later
  phase that asks "is this your account?" and uses eKYC for verified sellers.

### Password

Hashing uses argon2id with OWASP's minimum parameters (19 MiB, 2 iterations,
1 thread), stored as a PHC string. A sign-in that matches with older
parameters rehashes with the current ones. A semaphore allows 8 hashes at
once, because 500 parallel sign-ins at 19 MiB each would need almost 10 GB.

Passwords are 8 to 128 characters, follow no composition rules, and must not
appear in the embedded list of the 10,000 most common passwords (NIST SP
800-63B).

`POST /v1/auth/password/login` with `{identifier, password, device_name}`:

1. Detect phone or email and normalise.
2. Find the identity and the account's password.
3. When either is missing, hash a dummy value and return
   `invalid_credentials`, so the response time matches a wrong password.
4. After the password matches, check the status.
5. Create a session and return tokens.

Throttling uses `auth_throttle`, incremented with
`INSERT ... ON CONFLICT DO UPDATE`: five failures per identifier in 15 minutes
start an increasing wait; a wider limit applies per IP. Accounts are never
locked, since a lock lets anyone shut a victim out by typing wrong passwords.

Reset: `POST /v1/auth/otp` with `purpose: "reset_password"` returns the same
reply whether or not an account exists, and sends nothing when none does.
`POST /v1/auth/password/reset` with `{challenge_id, code, new_password,
device_name}` verifies the code and sets the password in one transaction,
revokes every session, and returns tokens for a new one.

`PUT /v1/auth/password` changes the password with the current one, or sets a
first password under the recent sign-in rule. Both revoke the other sessions.

### Google

App2 gets an ID token from Android Credential Manager.

1. `POST /v1/auth/google/nonce` returns `HMAC(NONCE_KEY, expiry || random)`,
   valid 5 minutes, stored nowhere. The app passes it to Credential Manager.
2. `POST /v1/auth/google` with `{id_token, nonce, device_name}`. go-oidc
   verifies signature, `iss`, `aud` (the shopnexus web client ID) and `exp`;
   the use case checks the nonce signature, its expiry, and that it equals the
   token's `nonce` claim.
3. In one transaction:
   - Identity `(google, sub)` exists: use its account and check the status.
   - Otherwise, when `email_verified` is true and identity `(email, email)`
     exists, link Google to that account.
   - Otherwise create an account (display name from `name`) with the Google
     identity, plus an email identity when Google verified the address and no
     account holds it.
4. Create a session and return tokens.

Linking only to existing identities, all of which are verified, stops the
pre-account takeover where someone registers a victim's email before the
victim ever signs in. Two parallel first sign-ins hit `UNIQUE (kind, value)`;
the store returns `ErrConflict` and the use case retries once.

Each check closes a different attack: the signature stops forged tokens, `iss`
stops other issuers, `aud` stops tokens Google issued to another app, `exp`
stops old tokens, the nonce stops replay of a leaked shopnexus token.

### Identities

`GET /v1/auth/identities` lists methods masked, plus whether a password is
set. `POST /v1/auth/otp` with `purpose: "add_identity"` and then
`POST /v1/auth/identities` with `{challenge_id, code}` add a phone or email;
a value held by another account returns `identity_taken`.
`POST /v1/auth/identities/google` links Google with the same checks as
sign-in. `DELETE /v1/auth/identities/{id}` refuses to remove the last
identity; a password does not count, since it needs a phone or email to be
used. Changing a phone number is adding the new one and removing the old one.

## Requirements on app2

- Refresh as a single flight: the first 401 starts a refresh, other requests
  wait for it and retry with the new token. On Android this is a `Mutex` in
  OkHttp's `Authenticator`. Parallel refreshes with one token look like a
  replay and revoke the session.
- Refresh when the access token has less than a minute left.
- Store the refresh token in EncryptedDataStore with a Keystore key.
- Map error `code` values to Vietnamese text.
- Send `device_name` at sign-in.

## Testing

| Layer | Files | Runs with |
|---|---|---|
| unit | `_test.go` beside entities and use cases | fakes only |
| integration | `_pg_test.go`, `_nats_test.go` beside adapters | Postgres and NATS from the test stack |
| E2E | package `e2e/` | the whole server in-process, real Postgres and NATS, fake vendors |

No build tags; all test code compiles on every run. Integration and E2E
tests call `testenv.RequirePostgres(t)` or `testenv.RequireNATS(t)`: under
`go test -short` they skip, and without `-short` a missing service fails the
test.

`testdb` migrates a template database once and clones it per test with
`CREATE DATABASE ... TEMPLATE`, dropped in `t.Cleanup`. It refuses to run
unless the DSN points at the test stack's port and database name. Tests that
need NATS use a stream and consumer names unique to the test.

Contract suites in `<module>test/` run against the fake and the Postgres store.

Named attack tests: pre-account takeover, 50 parallel OTP guesses, refresh
token replay, parallel refresh, a Google token with another `aud`, identical
OTP-send replies for known and unknown destinations, account B reading
account A's sessions.

Google verification is tested against an `httptest.Server` that serves a
generated JWKS and signs tokens with it.

Tests that cost money (a real SMS vendor, later) run only with `SMOKE_SMS=1`.

`make test-unit` runs `go test -short -race ./...`, `make test-int` runs
`go test -race ./internal/...`, `make test-e2e` runs `go test -race ./e2e/...`,
`make test` runs all three.

## Decision record

| Question | Decision | Reason given |
|---|---|---|
| Who types the code | the user | wants to understand and control the backend |
| Libraries | standard library first; pgx, go-oidc, kin-openapi, jwt, argon2, OTel, nats.go | Go needs few libraries |
| SQL | hand-written | easier to control performance with AI help |
| Layout | one file per use case; large modules keep use cases in the parent and one aggregate per subpackage | `server`'s account module had 43 use cases |
| Use case shape | a struct per use case holding only its dependencies, `Execute` plus `Handler` | each test builds only what its use case uses; close to the NestJS style the user knows |
| Store transactions | stores take a `Querier` argument, no tx in `context`, no unit of work | the handle a statement runs on is visible at the call |
| `account` and `auth` | two modules, `auth` imports `account` | identities and passwords belong to authentication |
| Sessions | JWT access 15 min plus refresh tokens in Postgres, no revocation list | write use cases check status; reads may lag 15 min |
| OTP concurrency | `SELECT ... FOR UPDATE`, no `version` column | `version` is for entities several people edit |
| IDs | UUIDv7 | bigint keys collided during past migrations |
| SMS vendor | log sender now, vendor later | |
| Password identifier | phone or email | |
| Google linking | automatic, to verified identities, when `email_verified` | |
| Side effects | outbox, relay, NATS JetStream | the user chose a broker from the start over Claude's suggestion of a Postgres queue behind the same API |
| Dormant phone accounts | step-up when another method exists; the single-method case later | |
| API | OpenAPI first, validated at runtime by kin-openapi | the spec is the single source of request shape |
| Versions | the newest release of every component, PostgreSQL 19 from its release candidate | the user's standing preference |
| Observability | slog, OTel, otel-lgtm | the user had only read logs before; traces check the hand-written SQL |
